# Pantry thin loop — increment 3: shelf life & "use this week"

- **Backlog item:** [BL-0029](../../backlog/BL-0029-pantry-shelf-life-expiry-nudges.md)
- **Date:** 2026-08-03
- **Status:** approved, implemented alongside this document

## Summary

Give pantry rows an approximate "use by" derived from a real per-item shelf-life
table, and spend that data on exactly one thing: a single batched "N items to use
this week → cook these" prompt that links to recipes which actually use them.

The user never types a date. There are no per-item nag badges.

## Context

[Increment 1](2026-07-18-pantry-thin-loop-design.md) deliberately refused a
time-based auto-expiry: *"an arbitrary staleness constant is a guess dressed up as
data."* It named the blocker precisely — `normalization.json` defined 5 items and
7 aisles, so a shelf-life table hung off it would have been almost entirely the
`other` bucket.

So the first half of this increment is data, not code.

## Design

### 1. The shelf-life table lives in Go, and only in Go

`normalization.json` gains two things:

```jsonc
"items": {
  "spinach": { "display": "Spinach", "aisle": "produce", "shelfLifeDays": 5 },
  "garlic":  { "display": "Garlic",  "aisle": "produce", "shelfLifeDays": 90 },
  ...
},
"aisleShelfLife": { "produce": 7, "meat": 3, "dairy": 10, "bakery": 5,
                    "pantry": 365, "frozen": 180 }
```

Resolution order is per-item → aisle default → **nothing**.

`other` is deliberately absent from `aisleShelfLife`. An item we failed to
recognize is an item whose shelf life we do not know, and inventing 7 days for it
is exactly the guess-dressed-as-data increment 1 rejected. Unknown items get no
`useBy` and never appear in a nudge.

The table grew from 5 items to ~115 across all six known aisles, chosen for
"what actually turns up on a weeknight grocery list" — the perishables that make
this feature worth having (spinach 5d, ground beef 2d, milk 7d, bread 5d) plus
enough shelf-stable staples that the pantry page isn't half `other`.

#### Guarded plural folding

A table of singulars is useless against real ingredient text, which is
overwhelmingly plural ("2 tomatoes", "3 eggs"). Rather than enumerate every plural
as a synonym, `CanonicalItem` folds a plural to its singular **only when the
singular resolves to a known item or synonym**:

- `-ies` → `-y` (strawberries → strawberry)
- `-es` → `` (tomatoes → tomato)
- `-s` → `` (eggs → egg)

The guard is what makes this safe. `asparagus` → `asparagu` is not a known item,
so the fold is discarded and `asparagus` passes through unchanged. Unknown plurals
behave exactly as they did before.

### 2. One new endpoint: `POST /normalization/lookup`

Convex must not carry a copy of the table — it would drift the moment either side
is edited, and the canonicalization rules (synonyms, plural folding) live in Go
anyway.

```
POST /normalization/lookup
{ "items": ["Tomatoes", "sriracha"] }

200
{ "items": [
    { "canonicalItem": "tomato",   "display": "Tomato",   "aisle": "produce", "shelfLifeDays": 5 },
    { "canonicalItem": "sriracha", "display": "Sriracha", "aisle": "other" }
] }
```

`shelfLifeDays` is omitted, not zeroed, when unknown — the wire format
distinguishes "no shelf life" from "expires today". Input is raw ingredient text,
so callers get canonicalization for free; duplicates collapse.

### 3. `useBy` is stamped where the purchase signal already is

Convex **mutations cannot do network I/O**, and `toggleItem` — the check-off hook
where an item enters the pantry — is a mutation. So the shelf life has to already
be in the database when the checkbox is ticked.

It rides in on the grocery list, which is generated by an *action*:

```
generateGroceryList (action)
  ├─ POST /grocery-list          → lines
  ├─ POST /normalization/lookup  → shelfLifeDays per canonicalItem   ← new
  └─ mergeGroceryList(lines, shelfLife)  → groceryList.shelfLifeDays
                                                    │
toggleItem (mutation, checked: true) ───────────────┘
  └─ upsertFromCheckoff(..., shelfLifeDays) → pantryItems.useBy
```

`useBy = Date.now() + shelfLifeDays * 86_400_000`, stamped in the **same
transaction** as the check-off, preserving increment 1's atomicity property.

Deliberate choices:

- **Both new fields are optional.** Pre-existing grocery and pantry rows stay
  valid; no migration. A row without `shelfLifeDays` simply never gets a `useBy`.
- **Re-checking refreshes `useBy`.** Ticking an item off is the purchase signal,
  so buying spinach again restarts its clock. This falls out of the existing
  upsert being idempotent-with-refresh.
- **`mergeGroceryList` takes a separate `shelfLife` map argument**, not a wider
  line shape. `groceryLineValidator` is pinned to the `@pantry/types` contract by
  a compile-time equality guard; widening it would force a change to a shared
  package other agents are actively editing, for data that is Convex-internal.
- **`useBy` is never cleared by the state cycle.** A row stepped to `out` keeps
  its date but is filtered out of nudges — the user is telling us they used it.

### 4. The nudge: batched, actionable, one surface

`expiringSoon()` (`apps/web/src/lib/expiry.ts`) is a pure function over pantry rows:
it keeps rows with a `useBy`, in state `have` or `low`, expiring within 7 days
(including already-past), sorted soonest-first. Pure so it is unit-testable
without React or Convex, and shared by both surfaces that render it.

`<UseItUp />` renders **one** card:

> **3 items to use this week** — Spinach (2 days), Chicken breast (tomorrow),
> Milk (5 days) · *Dates are estimates from typical shelf life, not printed
> labels.*
>
> [Recipes that use these →]

The recipe link is the whole point — the increment-1 design and BL-0021 both warn
that an alert without an action is a nag. `POST /recipes/using` answers it in Go,
where canonicalization already lives:

```
POST /recipes/using
{ "items": ["spinach", "milk"] }
→ [ { ...recipe, "matchedItems": ["spinach", "milk"] }, ... ]
```

It searches the caller's recipes **and** the shared catalog (a new user's pantry
would otherwise match nothing), ranks by match count then title, and caps at 5.
Convex exposes it as the `pantry.recipesToUse` action; the web layer loads it with
the `useAsyncData` primitive from BL-0012 so loading/error states are explicit.

**Where it renders:** Home (above the fold, since Home is the "what do I do now"
surface) and the Pantry page. Nowhere else, and never per-row. When nothing is
expiring the card renders nothing at all — no empty state, no zero badge.

**Honesty in the UI.** Every surface that shows a date says the date is an
estimate. The Pantry row chip reads `~5 days`, `~2 wk`, `~1 yr` — relative and
tilde-prefixed, because "use by Sep 12" reads like it was copied off a carton.
Past-due reads `~3 days ago`. The card carries the explicit disclaimer sentence.

### 5. Why not…

- **A Convex cron that expires rows automatically.** Deleting food the user may
  still have is worse than showing a stale row; the pantry's escape hatch is
  already the manual `have → low → out` cycle from increment 1.
- **Per-item badges on the grocery list.** The list is a shopping surface; expiry
  is a cooking concern, and the increment-1 design already established that the
  list is annotated only for don't-rebuy.
- **Storing `shelfLifeDays` on the pantry row** instead of a computed `useBy`.
  Then every read has to know the purchase date *and* the table, and re-buying
  wouldn't visibly reset anything. `useBy` is the fact the UI actually needs.
- **Caching the whole normalization table in Convex.** A copy is a copy; it drifts
  the moment the JSON is edited, which is precisely what this increment does.
- **A `GET /normalization` dump.** The lookup endpoint is bounded by what the
  caller already has, and pushes canonicalization to the side that owns it.

## Testing

| Layer | Coverage |
|---|---|
| Go (`normalize_test.go`) | per-item shelf life beats aisle default; aisle default applies; `other` yields none; plural folding folds known plurals and leaves unknown words alone |
| Go (`handler_test.go`) | lookup canonicalizes raw text, omits unknown shelf life, dedupes; `/recipes/using` matches user + catalog recipes, ranks by match count, ignores non-matches |
| Convex (`pantry.test.ts`) | `useBy` stamped from `shelfLifeDays`; absent when the line has none; refreshed on re-check; `expiringSoon` shape |
| Convex (`groceryList.test.ts`) | `shelfLifeDays` persisted by `mergeGroceryList`; check-off stamps `useBy` end to end |
| Web (`expiry.test.ts`) | window boundaries, state filter, ordering, relative formatting |
| Web (`UseItUp.test.tsx`) | renders nothing when empty; batches; shows the disclaimer; loads recipes |
| Web (`Pantry.test.tsx`) | approximate chip rendering |

## Deferred

- **Cook-decrement** (increment 2, BL-0028) still gates the most accurate signal
  that an item was consumed. Until it lands, `out` is set by hand.
- **Opened-vs-sealed shelf life.** Milk lasts 7 days opened and 3 weeks sealed;
  modelling that needs an "opened" event this loop does not have.
